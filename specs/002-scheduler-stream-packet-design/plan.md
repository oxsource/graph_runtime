# Implementation Plan: Scheduler-Node-Stream-Packet Module Interaction Design

**Branch**: `002-scheduler-stream-packet-design` | **Date**: 2026-07-23 | **Spec**: `/specs/002-scheduler-stream-packet-design/spec.md`

**Input**: Feature specification from `/specs/002-scheduler-stream-packet-design/spec.md`

**Note**: This plan follows a "总分总" (overview → individual → synthesis) approach: define the overall data flow, then design each module's responsibilities/boundaries/interfaces/internals, then synthesize the integration flow.

## Summary

Design the core module interaction contracts for Scheduler, Node, Stream, and Packet — the four modules that form the execution engine of Graph Runtime. Deliverables include: per-module interface contracts (`.h` files), entity definitions with state machines, module boundary descriptions, internal strategic decisions, and a consolidated data flow analysis showing how all four modules collaborate at runtime.

## Technical Context

**Language/Version**: C++17 (inherited from 001-project-architecture)

- All modules under `graph_runtime/src/` with Bazel BUILD targets

**Scale/Scope**: <50 Nodes per graph, single-process execution, JSON-only config

```text
graph_runtime/src/
├── stream/
│   ├── BUILD.bazel
│   ├── packet.h / .cc          (Packet implementation)
│   └── stream.h / .cc          (Stream implementation)
├── node/
│   ├── BUILD.bazel
│   ├── node.h / .cc            (Node base + lifecycle)
│   ├── graph_context.h / .cc   (GraphContext — per-invocation context)
│   └── node_factory.h / .cc    (NodeFactory — registry + creation)
└── scheduler/
    ├── BUILD.bazel
    └── scheduler.h / .cc       (Scheduler — topological event loop)
```

**Structure Decision**: One Bazel cc_library per module directory (stream, node, scheduler), following the established convention from the architecture plan. Packet is implemented within the stream module since it is the data unit that Streams transport. GraphContext and NodeFactory live in the node module since they are directly tied to Node execution.

## Phase 0 — Research: Design Decisions & Unknowns

### Unknowns Resolved

1. **Stream back-pressure policy**: How to signal upstream when downstream is full?
2. **Scheduler activation model**: How to detect "all inputs ready" efficiently?
3. **Node lifecycle threading**: What happens if Process() blocks?
4. **Packet ownership model**: Who owns Packet memory during transfer?
5. **Error propagation**: How does a Node error affect sibling/cousin Nodes?

See `research.md` for detailed findings.

### Phase 1 Outputs

### Module Design Approach (总分总)

1. **Overall data flow** (总): Trace one Packet through the entire system — Scheduler activates Node → Node reads from input Stream → Node processes → Node writes to output Stream → Scheduler notified → downstream Node activated
2. **Per-module design** (分): For each module — responsibilities, boundaries, interface contract, internal strategy
3. **Integration synthesis** (总): Re-consolidate the flow with all module contracts in place, showing the complete sequence diagram and collaboration patterns
